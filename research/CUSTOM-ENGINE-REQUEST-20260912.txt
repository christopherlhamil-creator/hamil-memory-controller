2. Encoding Design: How GGUF Weights are CodedGGUF relies entirely on the GGML block-quantization engine. Instead of encoding an entire matrix under a single precision rule, GGUF breaks the weight arrays down into small discrete blocks (usually 32 or 256 weights). Each block contains its own highly compressed metadata scales. [1] (https://huggingface.co/docs/hub/gguf), [2] (https://mbrenndoerfer.com/writing/gguf-format-quantized-llm-storage-inference), [3] (https://kaitchup.substack.com/p/choosing-a-gguf-model-k-quants-i)The Legacy Quants (Q4_0, Q4_1, Q8_0)These use classic, symmetric block quantization. [1] (https://www.reddit.com/r/LocalLLaMA/comments/1ba55rj/overview_of_gguf_quantization_methods/), [2] (https://kaitchup.substack.com/p/choosing-a-gguf-model-k-quants-i)The Math: A single block of 32 weights shares a single 16-bit floating-point Scale Factor (\(d\)).The Weights: The actual weights inside that block are squished down into simple, raw 4-bit integers (\(q\)).Dequantization: When the CPU/GPU reads them, it applies a simple fast multiplication per block: \(w = q \times d\). [1] (https://mbrenndoerfer.com/writing/gguf-format-quantized-llm-storage-inference), [2] (https://kaitchup.substack.com/p/choosing-a-gguf-model-k-quants-i)The K-Quants (Q4_K_M, Q5_K_S, Q6_K)This represents GGUF's biggest innovation: Mixed-Precision Super-Blocks. [1] (https://willitrunai.com/blog/quantization-guide-gguf-explained)The Logic: Not all parts of an AI model are equally important. Attention layers are highly sensitive to errors, while feed-forward network (FFN) layers are resilient. [1] (https://willitrunai.com/blog/quantization-guide-gguf-explained)The Structure: A K-Quant "Super-Block" contains a group of smaller blocks. It codes critical attention layers at a higher bit depth (like 5-bit or 6-bit) and aggressively drops non-critical matrices to 3-bit or 4-bit. [1] (https://huggingface.co/docs/hub/gguf), [2] (https://willitrunai.com/blog/quantization-guide-gguf-explained)The Formula: Weights are calculated dynamically via a formula like \(w = q \times \text{block\_scale} + \text{block\_min}\), using a 6-bit scaled threshold layer to protect crucial features while keeping the overall file size tiny. [1] (https://huggingface.co/docs/hub/gguf), [2] (https://willitrunai.com/blog/quantization-guide-gguf-explained)The I-Quants (IQ4_NL, IQ3_S)The most extreme compression layers use Importance Matrices and Lookup Tables (Quantization Dictionaries). Instead of computing linear scaling math on the fly, the weights inside the block are indexed pointers mapping directly to a hardcoded lookup table configuration optimized via an external calibration dataset. pub const CactusEngine = struct {
    model: *const c.CactusModel,
    raw_memory: []align(64) const u8, // Tracks the actual mmap bounds

    pub fn init(filepath: []const u8) !CactusEngine {
        // Open the model weights binary using native POSIX flags
        const file = try std.fs.cwd().openFile(filepath, .{ .mode = .read_only });
        defer file.close();
        const stat = try file.stat();

        // Map the entire binary file straight into virtual user space memory
        const mapped_bytes = try posix.mmap(
            null,
            stat.size,
            posix.PROT.READ,
            .{ .TYPE = .SHARED },
            file.handle,
            0,
        );

        // Cast the raw byte page frame pointer directly to our C model layout
        const model_ptr = @ptrCast(@alignCast(mapped_bytes.ptr));

        // Bare-metal validation check
        if (model_ptr.magic_signature != 0xCA07050517408) {
            posix.munmap(mapped_bytes);
            return error.InvalidModelSignature;
        }

        return CactusEngine{
            .model = model_ptr,
            .raw_memory = mapped_bytes,
        };
    }

    pub fn deinit(self: *CactusEngine) void {
        posix.munmap(self.raw_memory);
    }

    // Helper function to resolve relative binary pointers to physical memory slices
    inline fn getWeightsSlice(self: *const CactusEngine, layer: *const c.CactusLayer) []const f32 {
        const base_addr = @intFromPtr(self.model);
        const target_addr = base_addr + layer.weight_data_offset;
        const total_floats = layer.input_dim * layer.output_dim;
        
        const float_ptr: [*]const f32 = @ptrFromInt(target_addr);
        return float_ptr[0..total_floats];
    }

Feeding Your AVX-512 Assembly/C Kernels NativelyWhen it is time to compute matrix multiplications or run metrics on your Ryzen 8700F, you can pass resolved float array slices directly into optimized C execution kernels.By avoiding C++ virtual tables or hidden function overhead, the compiler translates this logic straight into fast assembly loops.kernels.cc#include "cactus_weights.h"
#include <immintrin.h> // Access native AVX-512 compiler intrinsics

void CACTUS_ALIGN execute_avx512_gemm(
    const float* __restrict__ input,
    const float* __restrict__ weights,
    const float* __restrict__ bias,
    float* __restrict__ output,
    uint32_t input_dim,
    uint32_t output_dim) 
{
    // The CPU can safely assume 64-byte alignment, optimizing cache lookups
    // and allowing __builtin_assume_aligned primitives to load vector pipelines.
    for (uint32_t i = 0; i < output_dim; i++) {
        __m512 acc = _mm512_setzero_ps();
        
        // Unrolled wide vector loops processing 16 single-precision floats at a time
        for (uint32_t j = 0; j < input_dim; j += 16) {
            __m512 in_vec = _mm512_load_ps(&input[j]);
            __m512 w_vec  = _mm512_load_ps(&weights[i * input_dim + j]);
            acc = _mm512_fmadd_ps(in_vec, w_vec, acc);
        }
        
        // Reduce and add bias data
        output[i] = _mm512_reduce_add_ps(acc) + bias[i];
    }
}
